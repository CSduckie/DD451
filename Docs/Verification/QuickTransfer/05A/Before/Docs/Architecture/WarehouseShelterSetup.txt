五、拖拽、滚动与生命周期

BeginItemDrag记录稳定实例、原Placement、朝向和抓取格偏移，申请本仓库的局部交互占用。真实旧占格和01归属一直保留；View仅绘制绿色/红色半透明预览。
每次拖拽有递增token。UpdateDrag与EndDrag必须携带当前token；CancelDrag清零后，迟到的OnEndDrag不能再次提交。
R由控制器Clone既有Player/RotateItem动作，只在本控制器有效拖拽期间改变预览朝向。05只启停和释放自己的动作，不启停共享Action Map，不接管Tab、F10或物品治疗。
松手时再次确认管理权限、交互占用、同一个权威实例、Owner/ContainerId、原摆放未被更改、可见目标格及矩形合法性，随后Manager.TryMove再次校验并提交。
越界、重叠、缝隙、关闭界面、控制器停用/销毁/换绑、应用失焦或暂停都会取消未提交预览。未由06接管的面板外松手同样取消；05本地逻辑不会自行丢地、转背包或生成世界物品。06已交付跨界面回调与自己的测试记录；05不据此冒称自己另行完成转移联验。
确认框和拖拽共享本仓库一个明确占用；HasPendingInteraction使首次升级在未结束操作时返回Busy。Claim/Release通过ContextChanged刷新资格按钮。上下文换到另一场景会清占用，旧控制器检测到失去OwnsInteraction时取消预览和确认。
04与05各自只处理自己的拖拽。06接入双向转移时必须保证一次拖拽只有一个活动来源及一份旋转预览；05没有建立全局拖拽或输入框架。

WarehouseView的cellSize是单格显示上限，初始字段默认52；gap默认3、padding默认8。实际格子边长读取EffectiveCellSize，按(viewport实际宽度－左右padding－列间gap)/仓库列数计算，并不超过cellSize，不由仓库行数决定。已保存926宽viewport下20列为42.65；本轮20×20→20×24只增行，因此在同一viewport与显示参数下，升级前后应保持42.65，旧格子及物品矩形尺寸不变。全列始终可见，格子仍为正方形，逻辑物品占格不改变。窗口宽度变化时允许按新viewport重新适配，不将这种响应式变化误记为升级缩放。
最新要求只上下滚动查看远端行。LockHorizontalScrolling会关闭横向滚动、隐藏遗留水平滚动条、清横向速度，并把Content的横向偏移归零。不能使用横向滚动补偿过窄面板；应调整右侧大面板和viewport宽度，使所有列仍可辨认和操作。
TryScreenToCell先刷新实际几何，检查viewport及EventSystem最上层命中，避免穿过遮挡面板提交；随后用RectTransformUtility.ScreenPointToLocalPointInRectangle转换滚动后的Content坐标，减去实际rect边缘与padding，最后除以EffectiveCellSize+gap。边距和格缝不是合法目标。物品矩形、抓取偏移和预览使用同一个EffectiveCellSize，不能按Inspector的cellSize上限反算落点。
View.LateUpdate在面板可见时比较几何尺寸，只在窗口、viewport宽度、仓库宽高或显示参数改变时重排。Controller.LateUpdate只在有效拖拽时重算鼠标落点，因此指针不动但滚动或窗口变化时也会更新预览。CanvasScaler缩放交给RectTransform转换处理，不使用固定世界深度。
窗口变化会复用并重排已有格子Image和ItemView；本轮20×20扩到20×24只在底部补足新增80个格子，不销毁重建原400格，不移动原Placement。稳定帧不重建格子。纵向滚动条不得在升级时通过AutoHideAndExpandViewport改变viewport宽度，避免间接缩放；现有接线使用固定预留纵条。双尺寸PlayMode已验证原400格与已有ItemView的对象、局部位置和矩形尺寸保持，并通过新增底部行拖放与全列指针命中；固定1920几何另有原始记录。切语言只RefreshText，不重建正在拖拽的ItemView。

六、EV来源和刷新时机

ShelterManager.RefreshEv逐项读取ItemManager.GetInstances()，对Definition有效、IsRetained为true、Owner仍为World/Container/Backpack/Storage的实例累加Definition.ev。同一登记表实例只计一次。
已保有布娃娃EV5和医疗包EV2即为7，即使两者都留在背包也成立；未保有的新战利品不计EV。05不因入仓而TrySetRetained(true)。
临时丢地只改Owner为World，01尚未取消保有，因此不能仅因落地扣EV。真正死亡、遗弃、撤离遗留由01.RecordLoss清除保有；Consumed、Lost和PendingRecovery不贡献EV。
CurrentEv是上次显示缓存，不是累计账本；没有AddEV或SpendEV。重复通知、容器变化、重开面板和语言切换不会增加EV。

目前01没有ItemsChanged/ItemUsed事件。实际刷新入口为：
- ShelterView.Bind/Open在打开或重绑时调用RefreshEv；打开仓库按钮也刷新一次。
- WarehouseManager完成移动/遗弃/显式完整通知后，Shelter订阅Warehouse.Changed；OnWarehouseChanged先CalculateEv写入缓存，再发一次Shelter通知。
- TryUpgrade在提交前再次RefreshEv，不能只相信上次按钮状态。
- 后续04完成使用、06完整转移、08损失/撤离保有结算之后，由08/09协调器明确调用ShelterManager.RefreshEv。

不能让04反向引用Shelter制造循环依赖；不要求01补事件总线。没有每帧复制GetInstances列表的EV轮询。
未交付模块的通知接入是待联验事项。测试驱动直接设置样本保有或测试中调用RefreshEv，不代表真实08结算或整条通知链已经完成。

七、首次免费升级的完整顺序

ShelterManager.TryUpgrade返回ShelterUpgradeResult：Success、NotReady、NotInShelter、AlreadyActivated、InsufficientEv、InvalidConfiguration、Busy。
方法内部解析有效依赖、重算EV，并检查当前明确的庇护所权限、首次尚未激活、EV门槛、升级配置、仓库合法性及没有拖拽/确认占用。当前要求目标宽度等于当前宽度且高度严格增长，资格查询和提交沿用同一校验入口；本轮EditMode已验证非法目标与非默认宽度。Shelter.Initialize会拒绝已停用组件；GetUpgradeAvailability也重新核对依赖有效性，但仅读EV缓存，不复制物品登记表。Button.interactable仅是显示提示，不替代方法检查。
成功顺序是：完整校验 → WarehouseManager.TryExpand静默扩容 → IsUpgradeActivated=true → Warehouse.NotifyChanged → Shelter的OnWarehouseChanged重算并统一通知。升级方法不再另发一遍相同的Shelter通知。
底层TryExpand不提前广播；监听者第一次看到成功时，尺寸和激活标记已一致。通知期间重入写操作被Busy拒绝，但CanExpand等只读查询仍能为UI显示最终资格。
升级不调用TryUseItem、RecordLoss或TrySetRetained，不扣EV、不扣物品。身份、归属、摆放、朝向、使用次数与保有状态全部保持。
未升级时EV7降到2会失去资格，重新达到7后可手动升级；已升级后EV降到2或0，尺寸和激活标记保持，重复点击返回AlreadyActivated。
Warehouse与Shelter用本次运行状态保存结果；重复Initialize、重新打开UI、普通场景切换不重置。新完整运行会通过SubsystemRegistration的session区分重新初始化，P0没有跨退出重启的磁盘持久化。

八、确认遗弃与唯一找回

选中仓库已有物品后点遗弃，控制器先取消拖拽，再保存PendingAbandonInstanceId并显示确认。确认身份是稳定实例ID，不依赖图标对象。
取消、关闭、换绑、失焦或场景权限失效只清临时目标，不修改归属、摆放或EV。切语言只按相同ID重绘正文，不更换目标、不确认遗弃。
确认时先检查界面权限和本控制器占用，并清空本次确认资格，避免双击重复执行；Manager随后重新检查真实登记、Storage归属、ContainerId及合法摆放。
Manager调用ItemManager.RecordLoss(instanceId, ItemLossReason.ShelterAbandonment)。失败返回LossRejected且原摆放不变；成功后按已验证ID移除仓库摆放，再统一Changed。
RecordLoss成功时Owner已经变为Lost或PendingRecovery，因此布局清理不能再次要求Owner==Storage。通知观察到的是完整结果，不依赖UI回调补第二次删除。
EV由Shelter从权威记录重新求和，不额外手动减一次。布娃娃遗弃后EV7→2，已升级尺寸仍保留。
唯一身份和OriginalSpawnPointId由01保留，下轮资格在其RecoveryRound中记录；05不创建替代实例、不立即生成地图物品。06/08后续负责真正下轮原点生成与流程联验。
